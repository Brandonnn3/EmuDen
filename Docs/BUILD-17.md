# Build 17 — game profiles, graphics controls and widgets

Each game can keep its own player preferences. Long-press its cover → **Game settings** → **Customize this game**. A separate atomic profile stores the resolution ceiling, asynchronous shaders, cached-shader preparation, texture sampling, picture sizing, top-screen balance and automatic-quality preference. Turning customization off returns to app defaults. Profiles are separate from the library catalog and game saves; malformed profiles cannot corrupt the library. Settings → Graphics & performance edits defaults. During play, Player Settings edits the current game's profile.

## Graphics and performance

Resolution, shader mode and texture sampling can now update as play resumes. The frontend drains pending GPU transfers before changing core options on its serial queue. The core's existing live-settings path reapplies per-game GPU accuracy settings before updating layout, avoiding an accidental accuracy-profile change. Native-save and snapshot formats remain unchanged.

**Automatic quality** is opt-in. The selected 1×–3× resolution is its ceiling. One-second core timing samples drive conservative changes: at least five consecutive poor/heat samples and 15 seconds since the previous change before stepping down; at least 30 healthy samples and 45 seconds before recovering a step. It never goes below 1× or above the chosen ceiling. An isolated shader hitch does not lower resolution. This is adaptive rendering quality, not a change to emulated CPU speed. Its effect on the physical Duo's thermals and frame pacing remains to be measured.

**Prepare known shaders before play** is opt-in. It uses the game's existing shader cache, reports startup stage progress and waits for queued cached pipelines before entering play. Startup can take longer; first encounters with unseen effects can still compile. The default background-compilation behavior remains available. The shader-cache card shows this game's cache size and offers a confirmed per-game reset only when it is closed. Matching is restricted to exact title-ID Vulkan shader/pipeline filenames; game saves, NAND, Mii resources and other games remain outside the operation. Selected cache files are staged before deletion so failed moves can roll back.

**Show frame-time graph** adds an optional overlay with video FPS, emulation speed, mean core time, the worst frame each second, current resolution and the system's heat status. It keeps 60 one-second samples and uses an equatable view so new game images do not require graph redraws. Heat is a system severity, not a Celsius measurement. Native timing is collected on the core queue; video counts use an atomic counter shared with the display worker. Pausing/restoring resets the sample window. The existing small FPS counter remains available when the graph is off.

Texture appearance offers **Game default**, **Crisp** and **Smooth** sampling. Game default retains the core's per-application choice. These adjust sampling, not the source texture detail. Picture sizing offers **Follow layout**, **Original proportions** and **Fill screen regions** independently of the shell. A flat-layout screen-balance control adjusts the available top/lower regions; the inner layout keeps its physical fold boundaries. Touch mapping follows the actual fitted lower image, excluding letterbox areas.

## Profile picture and Mii resources

The Mii settings portrait now accepts a chosen JPEG, PNG or HEIF image and persists it locally as a normalized 256-pixel JPEG, with a reset action. The file is bounded and decoded through the existing image validator; metadata is removed by the re-encode. A separate readiness badge follows the face-resource status.

The imported Mii resource archive supplies shared models. It does not identify a personal Mii to extract as an avatar. This feature is an image chooser, not automatic Mii rendering or selection. Personal Mii rendering would require separate profile data and a renderer. The settings text makes this distinction explicit. The avatar is not sent to the artwork site or included in widget snapshots.

## Native widgets

A WidgetKit extension supplies **Continue Playing** in small/medium sizes and **Recent Games** in medium/large sizes. It uses cinematic cached art, readable titles, play cues and an adapted clear/tinted presentation. Settings → Home Screen widgets previews the same content views; Home Screen layout/material still belongs to WidgetKit.

A shared App Group contains at most four recent game IDs/titles plus bounded downsampled JPEGs. Widget refresh is debounced and only requests timeline reloads when metadata or thumbnails change. Thumbnail reads never start artwork downloads and image work stops when artwork fetching is disabled for emulation. No ROMs, save states, Mii resources, account details or source code enter the shared snapshot. The extension performs no network fetches. Its file reads and decoded dimensions are bounded.

Game links accept only an exact `emuden://play/<UUID>` route. Missing games/files show a useful message. Switching from an active session goes through the existing resume-save and close flow; a failed save keeps that session open. A switch received during a state operation waits for it to finish before closing. The source and entitlements for both targets are included. The device app and widget have been built and signed with the same App Group in their signatures and provisioning profiles. Actual Home Screen pinning and live device behavior remain phone checks.

## Validation and delivery

Actual tests, captures, native renderer results and archive/source hashes are recorded in `build/TestFlight/Build17-PreparationReport.json`. **56 domain tests pass**, covering independent profiles, malformed data, cache isolation/symlinks, quality hysteresis, screen partitions, exact widget routes and cached artwork reads without networking. Four distinct UI scenarios have passing latest results: avatar persistence/reset, full outer-display touch mapping, per-game settings/widget previews, and URL launch/resume/missing-game handling. Large-widget clipping found in visual review was corrected and rechecked. Simulator rotation still leaves the display in portrait, so landscape geometry is domain-tested and its live appearance remains unverified.

The first widget-model test compared URL directory syntax including a trailing slash; it now compares the actual path. Initial UI passes exposed scroll/accessibility test assumptions; passing latest results and earlier bundles are retained. The first native graphics pass also exposed launch-argument values arriving as strings; preferences now use the appropriate UserDefaults accessors, with a regression test. The final actual Mario Golf run starts at 3×, switches to 1×, then 2×/Smooth and 3×/Game default, and completes 841 frames with successful state capture/restore. Raw top/lower image dimensions verify all scales. This run includes pauses and state work and is not a paired performance benchmark.

The URL test initially stopped at iOS's open confirmation, then exposed that XCTest's application URL API relaunches the process. The final UI scenario explicitly saves before cold URL launches and verifies the resume prompt, restore and missing-game message. A separate `simctl openurl` integration run exercises the active-session switch without relaunch, verifies both resume wrappers/checksums and the four-entry shared widget snapshot. It waits for fresh renderer logs rather than accepting a previous session's log. The queued-switch-during-state-operation path is implemented but that exact race was not forced. Earlier attempts remain in `build/`.

The artwork catalog grows independently: version 6 contains **40 backgrounds and 24 covers**. The latest scheduled pass added SteamWorld Dig, SteamWorld Heist, Bravely Second and Dragon Quest VII, with verified title IDs, unchanged PNG masters, delivery hashes/dimensions and anonymous/offline client checks. Prompt/provenance records are in `Docs/Design/ArtworkCatalog/batch-2026-11-11-1656.json`.

Signed builds 14, 15 and 16 and their matching source packages remain preserved. No physical-phone install, TestFlight upload or distribution IPA export is performed. No new physical FPS gain is claimed; Dark Moon's exact outdoor/window route, live folding/landscape, controller hardware, and sustained heat behavior remain unverified on the phone.

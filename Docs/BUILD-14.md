# Build 14 — 3DS frame transfers and resolution controls

Settings and Player Settings offer **1× (best performance), 2× and 3×** internal resolution. The preference applies when a game reopens. Native 1× remains the default and is already the core’s lowest supported scale; higher scales improve clarity and render four or nine times as many pixels. They cannot make a game faster than native 1×. Top-screen render sizes are 400×240, 800×480 and 1200×720; the bottom screen scales from 320×240 by the same factor. Invalid stored factors fall back to 1× in both the picker and the native bridge. The [pinned core’s resolution option](https://docs.libretro.com/library/azahar/#graphics) and its checked-in `core_settings.cpp` describe this quality/performance tradeoff.

## Frame transfer

The frontend previously waited for a GPU-to-CPU transfer and built the display image inside each core frame. An asynchronous worker now lets CPU emulation overlap that transfer. It waits for the current submitted frame, validates mapped memory visibility, copies its pixels into an owned image, then dispatches display work to the main queue. It delivers that completed frame immediately; it does not deliberately hold a previous frame until the next timer tick. The core exports one shared presentation image, so the frontend retains one sync index and waits for consumption before the core reuses that image. This moves transfer waiting and image construction off the emulation thread; it does not reduce the game’s underlying GPU workload. A preliminary two-index prototype was replaced after reviewing the core’s shared-image ownership; its measurements are retained separately and are not the final shipping comparison.

The implementation follows the [libretro Vulkan synchronization contract](https://github.com/libretro/RetroArch/blob/master/libretro-common/include/libretro_vulkan.h): stable sync indices, the matching slot mask, completion waits before resource reuse, same-queue image barriers, and completion before freeing resources. Pixel data stays valid through the worker callback and is copied before that buffer can be reused. Capture, restore, initialization and shutdown drain transfers. Worker errors propagate to the core queue. Session teardown also stops an abandoned bridge, and inactive bridges no longer close another session’s log.

The synchronous path remains available to the existing Mac smoke harness and to an iOS Simulator-only comparison override (`EMUDEN_TEST_GPU_PIPELINE=off`). Production uses asynchronous transfers. No device JIT, frame skipping, CPU underclocking or shader-accuracy reduction is introduced. The Azahar/MoltenVK frameworks and snapshot generation/format remain unchanged; native game saves keep their existing paths. The Option A library and search behavior remain. Catalog version 3 adds two original scenes; the app icon now uses an original glass handheld and portal.

## Measurement and verification

The final four-run ABBA comparison produced a median of 15.07 ms with synchronous transfers and 12.005 ms with asynchronous transfers, measured across 26 blocks of 120 core frames per mode. That is 20.3% less median emulation-thread frame time in this Mario Golf sequence. Median frontend transfer submission/blocking time changed from 1.29 to 0.02 ms. Both modes are capped near 60 FPS; this does not establish a phone FPS gain or a result for every game. Both 2× and 3× also passed real Mario Golf save/restore checks; raw post-restore PNGs confirm top/bottom sizes of 800×480/640×480 and 1200×720/960×720.

The paired timings use the final transfer implementation before later header/accessibility and icon polish; no post-polish or device FPS result is inferred. Performance evidence is recorded in `build/build14-performance-comparison.json`. The matched Mario Golf sequence uses an isolated QA simulator, a private copy of native saves/system data and the same warmed shader seed. Shader pauses are reduced in both modes; both use 1× and the same build-14 binary. Repeated synchronous/asynchronous runs separate transfer changes from startup/cache warming. The earlier build-13 run is retained for context. The first fresh-device run hit internal-disk exhaustion; that temporary simulator was removed. Transferred-cache startup attempts were also excluded from gameplay measurements. Only QA caches were reset. Original user saves remain untouched, and retired test-device fixture data is backed up on the SSD.

The existing log field named `GPU readback` now measures frontend CPU submission/blocking time in asynchronous mode. It is not GPU execution time. Full core-frame time and slow-frame counts remain separate. The simulator uses the Mac’s CPU/GPU and is capped near 60 core frames per second; lower frame cost demonstrates headroom, not a measured percentage FPS improvement on B Duo.

Final measured results, actual-resolution pixel checks, save/load checks, UI captures and signed archive/source verification are recorded in the build-14 preparation report and TestFlight status. Phone thermals, sustained FPS, controller haptics, the true inner display and Dark Moon’s exact freezing scene still require physical-device testing.

## Player header and FPS

During gameplay, the title/pause/menu header fades after three seconds without top-screen interaction. Tapping the top screen restores it. Lower-screen touch and virtual controls remain available and do not wake it. The standard layout overlays its header instead of reserving a permanent row; Duo panel mode retains its full-screen images. Loading, pause, state operations, errors, open menus/settings, input diagnostics and VoiceOver keep controls visible. Reduced Motion removes the fade animation.

Show FPS is available in Settings and Player Settings, off by default. When enabled, its counter stays in a small top-screen corner badge after the header fades. Player Settings keeps its heading and close action visible while scrolling. These changes do not alter game pixels or touch coordinates.

The verified local Mii resource installer is `build/Downloads/MiiTest/errfix.3dsx` (3DSX header, 7,243,584 bytes). Use Settings → Import Mii file; a decrypted Mii resource `.app` is also supported. `CFL_DB.dat` contains personal Mii records and does not replace face models. Close and reopen a game after importing. No Nintendo system archive is included in the app, public artwork site or source package.

Dark Moon’s iCloud file became available during this pass and was copied to the SSD for testing. Startup progressed through the initial loading sequence, but the Mac’s SimMetalHost service crashed in Apple AGX builtin/background shader compilation. EmuDen then terminated with METAL code 102 (XPC connection interrupted). The synchronous control reproduced the same failure at a similar loading point. These failed results and crash records are retained; no first-mansion walkthrough or phone fix is claimed.

## Icon and artwork expansion

The new opaque 1024×1024 App Store icon uses an original glass handheld with a directional cross, four face buttons and a cyan/violet portal display. Its unchanged square master and reproducible exporter are in [Branding](Branding/README.md). The old icon is preserved in build 13 and a private build backup.

Public artwork catalog version 3 retains all 52 previously delivered images and adds Kirby Planet Robobot and Pilotwings Resort scenes: 30 scenes and 24 generated covers across 30 entries. The two new scenes were generated with built-in image_gen, visually inspected, and delivered as content-addressed JPEGs. The native Swift catalog client fetched both anonymously, verified their digests/metadata, upgraded the catalog and reused both with networking disabled. The earlier collection's 52-image verification remains separate. These are original fan illustrations, not screenshots or compatibility claims.

A 44-title expansion queue is tracked in [the catalog design folder](Design/ArtworkCatalog/README.md). Three output rejections (Mario Kart 7, Detective Pikachu and Star Fox 64 3D) retain existing fallbacks and are not retried automatically. Two entries are accepted; later runs pick pending titles. Hourly thread follow-ups are scheduled through 08:00 America/New_York on 2026-11-12, subject to normal usage and the Mac/app remaining available. They preserve the signed build-14 archive/source snapshot and publish catalog additions independently.

The final HUD implementation animates opacity on a stable toolbar, disables its hit testing and hides its accessibility content. An earlier removal transition left the glass drawn during the continuous emulated-image updates; screenshots caught this despite an accessibility-only test passing. Final direct Simulator captures and release UI captures confirm no residual toolbar. A top-screen accessibility value reports control visibility; test helpers explicitly wake controls before using them because Simulator accessibility can retain invisible element entries.
